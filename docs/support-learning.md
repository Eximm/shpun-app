# Обучение поддержки на обращениях — первая внедрённая версия

## Что работает

В админке поддержки появился раздел «Знания из обращений». API анализирует
обычные обращения при запуске и каждые пять минут, а также по кнопке.
Пакеты по 100 диалогов чередуются; кнопка обрабатывает до 200 за один запрос.
Статистика показывает разобранные диалоги, предложения, одобренные знания,
применения и подтверждённые решения.

Из закрытого/решённого обращения с содержательным ответом сотрудника создаётся
черновик: исходный вопрос, ответ, признаки, услуга и ссылки на сообщения.
Отдельно отмечается явное подтверждение клиента. Обычное «спасибо» и
«не получилось» подтверждением не считаются. Открытые и неразобранные случаи
учитываются, но не становятся автоматическими инструкциями.

Это локальное накопление проверяемого опыта, не дообучение весов нейросети.
Внешняя модель и облачная отправка переписки не подключены: в действующем
ShpunApp нет настроек провайдера. Анализ первой версии — прозрачное извлечение
вопроса, последнего содержательного ответа сотрудника и признаков результата.
Он не заменяет смысловую оценку сотрудником и может предложить неполную карточку.

## Проверка сотрудником

1. Открыть раздел и нажать «Проанализировать диалоги» либо дождаться фонового прохода.
2. Открыть исходное обращение; проверить, что найден именно полезный ответ.
3. Переписать карточку в общий совет: без конкретного клиента, оплаты, срока,
   личных данных и неподтверждённых выводов.
4. Указать минимум два обязательных признака. Для автоответа должны совпасть
   все признаки и категория услуги (если она есть у исходного случая).
5. Подтвердить проверку и одобрить. При необходимости отдельно включить автоответ.

По умолчанию карточки — черновики и к ответам клиентов не допускаются.
Условия, требующие интерпретации сотрудником, делают карточку только подсказкой:
если поле ограничений заполнено, автоответ не разрешается. Запрещены автоответы
про оплату, переносы, пароли, сбросы и удаление настроек. Проверки регулярными
выражениями — дополнительная защита, не замена проверке содержания сотрудником.

Ссылки, email, IPv4, длинные ключи, телефоны и известное имя клиента скрываются
при создании черновика. Автоматическая очистка не гарантирует удаления всех
возможных персональных данных; поэтому проверка обязательна.

## Как используются знания

Шпунь сопоставляет последние сообщения текущего клиента с одобренными карточками.
Используется нормализация слов и прозрачное лексическое сопоставление, без
семантических embeddings. Сходные, но иначе сформулированные вопросы могут
не найтись — тогда работает прежний сценарий или передача сотруднику.

Для подсказки сотруднику требуется совпадение минимум двух признаков и 65%.
Для самостоятельного ответа — всех признаков, явного разрешения автоответа
и отсутствия близкого конкурирующего решения. Источник должен оставаться
закрытым/решённым и неизменённым. Удаление, редактирование или повторное открытие
источника сразу исключает его из поиска; фоновый проход возвращает одобренную
карточку на проверку. Архивирование прекращает дальнейшее использование.

Остаются действующими ограничения Шпуня: просьба о человеке имеет приоритет,
известный сбой отменяет подбор локальных советов, два безуспешных шага ведут
сотруднику, после ответа сотрудника бот молчит. Вложения изучает человек.

Каждое применение хранит номер карточки и версию, исходное сообщение клиента
и ответ помощника. Явное подтверждение результата отмечается как `confirmed`,
передача — `handoff`. При передаче создаётся внутренняя заметка с причиной,
шагами и последними сообщениями. Эти заметки не видны клиенту.

## API и хранение

Все endpoints требуют существующей проверки администратора:

* `GET /api/admin/support/learning` — карточки и агрегаты.
* `POST /api/admin/support/learning/analyze` — пакет анализа.
* `PATCH /api/admin/support/learning/:id` — проверка/одобрение/отклонение/архив,
  с номером версии для защиты от одновременного редактирования.
* Подсказки по тикету дополнены полем `learned`; обычный пользователь этого API
  не получает. Клиенту не раскрывается переписка других людей и ссылка на источник.

Добавочные таблицы в текущей SQLite: `support_learning_reviews`,
`support_learned_cases`, `support_learning_uses`. Миграции создаются при старте,
существующие тикеты не переписываются. В будущем при смене backend поддержки
этот локальный порт нужно переносить вместе с тикетами.

Отключение фонового анализа: `SUPPORT_LEARNING_ENABLED=false`.
Отключение только применения изученных решений: `SUPPORT_LEARNED_REPLIES_ENABLED=false`.
Общее отключение помощника: `SUPPORT_ASSISTANT_ENABLED=false`.
Переменные можно задать в существующем env_file API и пересоздать API.
Старые ручные сценарии и работа сотрудников сохраняются.

## Проверки и границы результата

Тесты проходят полный путь: новый случай → извлечение → одобрение → ответ
другому клиенту → подтверждение результата. Проверены права доступа,
персональные данные, неподтверждённые результаты, неоднозначные совпадения,
удаление источника и смена статуса без нового сообщения.

Ни одна реальная карточка не одобряется автоматически при внедрении.
Поэтому первый разбор даёт реальные предложения для проверки, а не обещание,
что Шпунь уже научился безошибочно решать все накопленные случаи.
Следующий слой — подключение согласованной модели для смыслового обобщения,
поиска перефразированных случаев и подготовки ответа по проверенным источникам.
