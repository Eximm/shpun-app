# Помощник Shpun

## Как работает

Помощник работает внутри существующего обращения. Кабинет сразу открывает
переписку после создания тикета. Кнопка «Позвать сотрудника» доступна без
предварительных вопросов; слово «оператор» работает в кабинете и Telegram.
Telegram показывает ответы при открытии переписки через существующий шаблон,
первый ответ содержит имя помощника и способ позвать человека текстом.

Максимум два простых диагностических ответа на тикет, каждый сценарий — один
раз. Если устройство неизвестно, помощник спрашивает его и использует ответ
только в контексте этого вопроса. Неизвестный вопрос, «не помогло», повтор
сценария, вложение или просьба о человеке переводят разговор сотрудникам.
После ответа или назначения сотрудника бот больше не вмешивается.
Состояние сохраняется после перезапуска. Изображения автоматически не читаются.

Все обращения с самого начала видны сотрудникам. Ответы помощника оставляют
статус `waiting_staff`, а запрос кнопкой создаёт сообщение клиента, которое
попадает в действующие непрочитанные и уведомления поддержки. Повтор кнопки
не создаёт дубликатов. Передача означает существующую очередь поддержки,
а не назначение конкретного человека или обещание немедленного ответа.

После явного «всё работает» помощник один раз предлагает закрыть обращение
и по желанию оставить отзыв в существующем разделе ShpunApp «Отзывы».
Сам тикет не закрывает. Если проблема вернулась, передаёт сотруднику.
Открытая переписка кабинета обновляется каждые 10 секунд; набранный текст
и вложения при обновлении сохраняются.

Это помощник на правилах: отдельные ключи ИИ и расходы на генерацию не нужны.

В кабинете он представляется как «Шпунь» с подписью «Автоматический помощник».
Новый ответ после отправки показывается через 1,6 секунды с индикатором
«Шпунь печатает…». Это оформление уже сохранённого ответа, без задержки API
и вызова сотрудника. При открытии истории сообщения не проигрываются заново.
Приветствие записывается один раз, дальнейшие короткие подтверждения вроде
«перезагрузил» продолжают текущий шаг. Анимация учитывает reduced-motion.

## Файлы и API

* `api/src/modules/support/knowledge.json`: 25 сценариев со всеми темами задания,
  триггерами, внутренними проверками, простыми ответами, шагами и эскалацией.
  Между группами триггеров AND, внутри OR; регистр, пробелы и ё нормализуются.
* `assistant.ts`: кандидаты сценариев и подсказки сотруднику.
* `assistantRuntime.ts`: автоматический диалог и передача человеку.
* `voice.json`, `voice.ts`: 110 оригинальных реплик для приветствия, уточнения,
  результата шага, вложений, повторной проблемы, передачи и завершения,
  а также варианты самих вопросов и советов. Выбор зависит от типа реплики
  и сохранённого хода разговора; повтор запроса не меняет ответ.
* `assistantState.ts`: добавочная таблица `support_assistant_state` в текущей
  `linkdb.sqlite`, сохраняет режим, причину, последний обработанный запрос,
  использованные сценарии и число ответов. Миграция создаётся при старте.
* `service.ts`: запуск после сохранения сообщения и остановка при ответе или
  назначении сотрудника. Ошибка помощника не отменяет сообщение клиента.
* `routes.ts`: `POST /api/support/tickets/:id/staff`, только владелец тикета.
* `adminRoutes.ts`: `GET /api/admin/support/tickets/:id/assistant`, только
  администратор. Его `autoSend=false` относится к подсказкам сотруднику;
  автоматические ответы выполняются отдельно в runtime после записи сообщения.
* `Support.tsx`: имя, кнопка сотрудника, открытие и обновление переписки.
* `AssistantSuggestions.tsx`, `admin/SupportSection.tsx`: сворачиваемые подсказки
  с проверками и следующими шагами. Шаблон вставляется только в пустое поле,
  отправку сотрудник выполняет сам.
* `dict.ts`, `index.css`: переводы интерфейса и адаптивная строка помощника.
* `docker-compose.yml`: включение и необязательный текст известного сбоя.
* `assistant*.test.ts`, `routes.test.ts`, `api/package.json`: тесты и их запуск.

Запрос кнопки, ответ и состояние сохраняются одной SQLite-транзакцией.
Runtime сейчас рассчитан на действующий SQLite; будущая замена backend тикетов
потребует перенести этот порт вместе с тикетами.

## Что требует проверки сотрудником

SupportShmPort получает личность и принадлежащую пользователю услугу.
Срок, статус, имя и категория — снимок на момент создания обращения.
Нет API устройств Remnawave, лимита/last seen, скачивания подписки, реального
соединения, переноса Amnezia → Flex и расчёта остатка срока. Нет автоматической
связи ошибки выдачи подписок с мониторингом. Не подтверждены текущие правила
прекращения Amnezia, доступность Hysteria2 у конкретной услуги и приложений
по регионам App Store.

Такие случаи передаются сотруднику. В подсказках проверки имеют статус
`unverified`: сотрудник сверяет аккаунт и историю сам. Помощник не объявляет
сервер исправным по одному импорту или записи устройства, не переносит срок,
не сбрасывает устройства и не навязывает Flex. Внутренние детали не отправляются
клиенту. Поддержка Amnezia не объявляется прекращённой без подтверждения.

Источники: последние пять доступных пар сообщений исходного чата
`6aaf910f-fd6c-83eb-befc-17d1350b45f2` и перечень кейсов из задания.
Более раннюю историю API не вернул; это не полный экспорт чата.

Дополнены бытовые ситуации: низкая скорость, один неработающий сайт/приложение,
разница Wi-Fi и мобильной сети, обрывы и проверка оплаты. При низкой скорости
помощник уточняет сеть и масштаб проблемы, затем предлагает сравнение без
подключения. Проверку оплаты выполняет сотрудник, зачисление не выдумывается.

При подготовке оригинальных формулировок использованы принципы разговорной
поддержки: короткие реплики, реакция на контекст, понятный переход к человеку
и отсутствие неподтверждённых обещаний. Это рекомендации по общению, а не
источник технических фактов или правил тарифов:
[Intercom: botiquette](https://www.intercom.com/blog/botiquette-designing-impactful-chatbots),
[Intercom: customer support](https://www.intercom.com/help/en/articles/198-our-best-practice-guide-to-customer-support).

## Сборка на сервере

Ветка `feat/support-knowledge`. Из существующего checkout ShpunApp:

```sh
git fetch origin
git switch feat/support-knowledge
git pull --ff-only origin feat/support-knowledge
docker compose --env-file /opt/shpun-app/.env build shpun-app-api shpun-app-web
docker compose --env-file /opt/shpun-app/.env up -d shpun-app-api shpun-app-web
```

Серверные команды выполняет пользователь. Если checkout содержит изменения,
сначала сохранить их обычным рабочим порядком; `reset --hard` не нужен.
Существующие тома данных используются как раньше, таблица состояния добавляется
автоматически. В Compose помощник включён по умолчанию. В `/opt/shpun-app/.env`:

```dotenv
SUPPORT_ASSISTANT_ENABLED=true
SUPPORT_ASSISTANT_INCIDENT_TEXT=
```

При запуске API вне Compose явно задать `SUPPORT_ASSISTANT_ENABLED=true`.
При подтверждённом общем сбое можно задать простой пользовательский текст
в `SUPPORT_ASSISTANT_INCIDENT_TEXT` и пересоздать API. Связанные новые обращения
получат этот текст и перейдут сотруднику без локальных переустановок.
Не добавлять неподтверждённый срок восстановления; после сбоя очистить текст.

Отключение без отката кода: задать `SUPPORT_ASSISTANT_ENABLED=false` и выполнить:

```sh
docker compose --env-file /opt/shpun-app/.env up -d --no-deps --force-recreate shpun-app-api
```

Обычная поддержка, кнопка сотрудника и история сохраняются. После повторного
включения бот не возобновит диалог в уже переданных сотрудникам тикетах.

## Проверки

API: `npm run test:support`, затем `npm run build` из `api`. Проверяются реальные
временные SQLite, предел шагов, вложения, непрочитанные, права доступа,
откат неуспешной транзакции, перезапуск отдельного процесса и отключение.
JSON включается в скомпилированный `dist`, который копирует Dockerfile.

Web: TypeScript без incremental, `check:i18n`, `check:hardcoded`, действующие
проверки сообщений/истории/адаптивности и production-сборка Vite.

Production и действующий Telegram-диалог агент не изменял. После вашей сборки
проверить новое обращение «Windows Happ нет интернета», немедленный вызов
сотрудника, непрочитанное у поддержки и отсутствие ответов бота после человека.
