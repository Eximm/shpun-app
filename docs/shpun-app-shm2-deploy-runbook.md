# Переходная выкладка ShpunApp на SHM 2.x

Цель — выпустить ShpunApp, совместимый с SHM 2.x и будущим SHM 3.x, не обновляя сам биллинг. Команды выполняются последовательно; после каждой фазы проверяется критерий продолжения.

## 1. Preflight без изменений

1. Запустить `deploy/inspect-shpun-app-production.sh` на сервере.
2. Убедиться, что checkout находится на ожидаемом commit и рабочее дерево чистое.
3. Записать image ID, restart count и время старта обоих контейнеров.
4. Проверить API `/health`, `/api/health`, web и счётчик ошибок за последний час.
5. Убедиться, что `SHM_OAUTH_PROVIDERS` и `OAUTH_CALLBACK_BASE_URL` отсутствуют или пусты.

Если checkout грязный, health неуспешен или уже есть необъяснённые ошибки, выкладку не начинать.

## 2. Точка возврата

1. Создать каталог backup с timestamp и правами только для root.
2. Создать согласованную SQLite-копию штатной командой `.backup`, а не копированием одного файла в WAL-режиме.
3. Выполнить `PRAGMA quick_check` на созданной копии; результат обязан быть `ok`.
4. Скопировать текущий `.env` в защищённый каталог, не печатая его содержимое.
5. Пометить текущие API и web image ID локальными rollback-тегами с коротким исходным commit.
6. Сохранить текущий compose-файл и его SHA-256.

Любая ошибка на этой фазе запрещает продолжение.

## 3. Получение точного кода

1. Выполнить `git fetch origin`.
2. Проверить, что ожидаемый commit существует и является потомком текущего production commit.
3. Выполнить fast-forward до точного SHA, уже проверенного локально. Не использовать непроверенный новый HEAD ветки.
4. Повторно проверить чистоту дерева и SHA Dockerfile/compose.

## 4. Сборка и переключение

1. Собрать API и web из Dockerfile с закреплёнными digest базовых образов.
2. Не использовать `--pull` и не обновлять SHM-контейнеры.
3. Пересоздать только `shpun-app-api` и `shpun-app-web`.
4. Дождаться running-state и проверить, что restart count не растёт.

## 5. Smoke на SHM 2.x

Проверять не только HTTP-статус, но и ответ и сохранённое состояние:

- обычный вход существующего пользователя;
- новая регистрация с паролем не короче 10 символов;
- регистрация с referral/partner attribution;
- установка, отправка кода, подтверждение и удаление email;
- смена пароля и вход новым паролем;
- password reset по ссылке;
- Telegram Mini App/Login Widget: вход и регистрация;
- чтение и изменение имени/телефона;
- список услуг, заказ и прогноз;
- список платёжных систем без проведения реального платежа;
- отсутствие OAuth-кнопок при выключенном feature flag.

После smoke повторно проверить логи и restart count. Изменение billing-template `profile.set` проводится отдельной контролируемой фазой с экспортом активного template и собственным rollback.

## 6. Abort и rollback

Откат начинать при цикле рестартов, неуспешном health, невозможности входа, ошибках основных API-сценариев или повреждении локальной session-БД.

1. Остановить только новые ShpunApp-контейнеры.
2. Вернуть контейнеры на сохранённые rollback image tags.
3. Вернуть прежний Git commit способом, не уничтожающим неизвестные изменения.
4. SQLite восстанавливать только если новая версия действительно изменила или повредила данные; перед восстановлением сохранить аварийную копию текущего состояния.
5. Повторить health, вход и базовые пользовательские сценарии.

Обновление SHM 3.x выполняется позже по `docs/shm-3-staging-runbook.md` и не является частью этой процедуры.
